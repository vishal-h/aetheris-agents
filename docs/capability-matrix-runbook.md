# Capability Matrix — Runbook

`docs/capability-matrix.md` is generated by a set of dog-fooding agents that
read this repo and document themselves. It lists every agent, its tools, and
every script with its one-line purpose across all use cases.

---

## Generating the matrix

```bash
cd ~/sandbox/elixirws/aetheris
./scripts/sprint.sh capability_matrix
```

Nine sub-agents run sequentially (one per use case), then
`scripts/assemble_matrix.py` combines the sections and computes the derived block.
Output is written to `docs/capability-matrix.md`.

The assemble step is deterministic — no LLM. Every number, the unique-tools line and
both overlap tables are counted from the sections' own table rows (BL-067). Curated
cells survive the regen because they live in `docs/capability-matrix-overrides.json`,
which the assembler merges before it counts (BL-068) — a full regen is safe.

Commit after each run:

```bash
cd ~/sandbox/elixirws/aetheris-agents
git add docs/capability-matrix.md
git commit -m "docs: update capability matrix"
git push
```

---

## When to re-run

Re-run whenever:
- A new use case directory is added
- A new agent file (`.exs`) is added to any use case
- A new script (`.py` or `.exs`) is added to any use case's `scripts/` directory
- An existing agent's tool list changes
- An existing script's one-line docstring changes

Adding a new agent or script to an existing use case requires no file changes —
just re-run the sprint and commit the updated matrix.

## How it works

```
agents/capability_matrix_{uc}.exs      ← one per use case, runs standalone (LLM)
scripts/assemble_matrix.py             ← assembler, runs after all sections (deterministic)
docs/.sections/{uc}.md                 ← intermediate files (gitignored, disposable)
docs/capability-matrix-overrides.json  ← curated cells (committed, durable)
docs/capability-matrix.md              ← final output (committed)
```

Each sub-agent reads only its own use case directory (≤ 10 files, ≤ 15 steps).
The assembler reads the section files and writes the final matrix with an overlap
report and summary table.

`assemble_matrix.py` pastes section content verbatim and derives everything else by
counting rows:

| Derived value | Rule |
|---------------|------|
| Summary counts | Agents/Scripts table row count per section; totals are sums |
| Unique tools | backticked tokens of each Tools cell, first-appearance order; a cell with no backticks (e.g. `MCP servers (corpus_search, lattice)`) counts as one entry |
| Identical tool sets | agents grouped by tool-*set* equality (cell order does not split a group), groups of ≥ 2, largest first |
| Script name overlaps | a script row name appearing in more than one section |

Section order is the `SECTIONS` constant at the top of the script — not directory
order. A section file whose key is not in `SECTIONS` is ignored with a stderr WARN;
a missing section file yields "_Section not available._", a 0/0 Summary row, and
exit 1 (partial matrix).

Two runs of the **assembler** over unchanged sections produce byte-identical output. The
section step above it does not share that property — it is an LLM, and regenerating a section
rewords cells whose source has not changed — so a matrix diff carries rewordings as well as
real changes, and needs reading rather than skimming.

## Curated cells

Section files are regenerated by an LLM on every run, so any text a human wrote by
hand — milestone provenance in a script's purpose, a prose capability in a Tools cell
— would be reworded away. `docs/capability-matrix-overrides.json` is where that text
lives instead. It is **committed**; `docs/.sections/` is not.

```json
{
  "docbuilder": {
    "scripts": {
      "generate_pdf.py": { "purpose": "… Jinja2 path added in m6 (`has_jinja: true`)." }
    }
  },
  "provenance": {
    "agents": {
      "search_agent.exs": { "tools": "MCP servers (corpus_search, lattice)" }
    }
  }
}
```

- Keyed by use case → `agents` / `scripts` → row key → field.
- Agent row key is the **agent file name**, or `file.exs::Label` when one file
  contributes several rows to a section (an OrbConfig with several RunConfigs).
  Overridable fields: `label`, `tools`. Script row key is the script file name;
  field: `purpose`.
- **A bare file key applies to every row with that file name.** For a file that
  contributes more than one row, always use `file.exs::Label` — a bare key would put
  the same curated cell on all of its rows. Today only single-row files are keyed
  bare, and this is the rule that keeps it that way when one of them gains a second
  RunConfig.
- Top-level keys beginning with `_` are comments and are ignored.

The merge happens **before** anything is counted, so an overridden Tools cell flows
into the unique-tools line and the overlap tables exactly as a generated one would —
the emitted table and the derived block never disagree.

**An override that matches no row fails the run** (exit 1, so the sprint reports it).
That is deliberate: if a script is renamed upstream, its curated purpose would
otherwise vanish from the matrix silently, which is the whole failure this file
exists to prevent. Fix it by renaming the key or deleting the entry. A missing
overrides file warns and assembles without curation; an unreadable one fails, because
it drops every override at once.

## Re-running a single section

If one sub-agent fails (rate limit, etc.) and the others succeed:

```bash
cd ~/sandbox/elixirws/aetheris
mix aetheris run ../aetheris-agents/agents/capability_matrix_{use_case}.exs
python3 ../aetheris-agents/scripts/assemble_matrix.py

cd ~/sandbox/elixirws/aetheris-agents
git add docs/capability-matrix.md
git commit -m "docs: update capability matrix"
```

This is a convenience, not a safety measure: a full regen no longer loses curation
(see **Curated cells** below), so re-running one section is simply cheaper and gives
a smaller diff. Section files are disposable scratch — anything that must survive a
regen belongs in the overrides file.

## Adding a new use case

**1. Create the directory structure:**

```
{use_case}/
  agents/    ← .exs agent files
  scripts/   ← .py and .exs scripts
```

**2. Add a sub-agent file:**

```bash
cp agents/capability_matrix_email.exs agents/capability_matrix_{use_case}.exs
```

Edit the new file — change these four values in the system_prompt:

| Field | Change to |
|-------|-----------|
| `agents_dir` | `"{use_case}/agents"` |
| `scripts_dir` | `"{use_case}/scripts"` |
| `section_title` | human-readable use case name |
| `section_file` | `"docs/.sections/{use_case}.md"` |

Also update `run_id` and `label`. Keep all other fields unchanged.

> **Note:** Step 3 of the system_prompt already collects both `.py` and `.exs` files
> from `scripts/`. For `.exs` scripts the sub-agent extracts the purpose from the
> opening `#` comment rather than a docstring. Do not revert this to `.py` only.

**3. Update the assembler:**

Add the new use case to the `SECTIONS` constant in `scripts/assemble_matrix.py`,
in the position it should occupy in the matrix:

```python
("{use_case}", "{summary label}"),
```

The label is what the Summary table and the overlap tables print. Nothing else in
the script is per-use-case.

**4. Add to sprint.sh:**

In `aetheris/scripts/sprint.sh`, find the `capability_matrix` case and add
a `run_agent` call before the assembler:

```bash
run_agent "cap-matrix-{use_case}" "$OUT_DIR/capability_matrix/{use_case}.json" \
  "../aetheris-agents/agents/capability_matrix_{use_case}.exs" \
  || warn "cap-matrix-{use_case} failed — section will be missing"
```

**5. Commit both repos:**

```bash
# aetheris-agents
git add agents/capability_matrix_{use_case}.exs \
        scripts/assemble_matrix.py
git commit -m "feat(capability-matrix): add {use_case} sub-agent"

# aetheris
git add scripts/sprint.sh
git commit -m "feat(sprint): add {use_case} to capability_matrix case"
```

**6. Re-run and commit the updated matrix.**

If the new section carries hand-written text the section agent would not reproduce
(milestone provenance, a prose Tools cell), add it to
`docs/capability-matrix-overrides.json` — see **Curated cells**.

Values for this use case:

  scripts_dir   = "{use_case}/scripts"
  section_title = "{Section Title — Human Readable}"

Source file to copy: agents/capability_matrix_email.exs
(or whichever capability_matrix_{uc}.exs exists — pick any one)

Work in aetheris-agents/ for agent files, aetheris/ for sprint.sh.

After Claude Code completes, verify the four changed values in the new
sub-agent file, then re-run and commit:

```bash
./scripts/sprint.sh capability_matrix
cd ~/sandbox/elixirws/aetheris-agents
git add docs/capability-matrix.md
git commit -m "docs: update capability matrix"
```

## Known limitations

**Assembler section list is explicit.** Adding a new use case requires adding it to
`SECTIONS` in `scripts/assemble_matrix.py` (Step 3 above). This is deliberate — the
matrix order is a decision, not directory order — but it means a section file with no
`SECTIONS` entry is skipped. The script names it on stderr rather than dropping it
silently.

**Stale sections after removing a use case.** Section files in `docs/.sections/`
persist between runs. If a use case is removed, drop its `SECTIONS` entry and delete
its section file:

```bash
rm docs/.sections/{use_case}.md
python3 scripts/assemble_matrix.py
```

**Rate limits cause partial matrices.** The `|| warn` in sprint.sh lets the
sprint continue when a sub-agent hits a rate limit. The assembler writes
"_Section not available._" for the missing section, prints a WARN and exits 1, so the
sprint reports the matrix as partial. Re-run the failing sub-agent after the rate limit
clears (usually 60 seconds), then re-run the assembler.

**api/ uses a two-level structure.** The api use case has separate tenant and
gateway sub-agents (`capability_matrix_api_tenant.exs` and
`capability_matrix_api_gateway.exs`) because its directory structure is
`api/tenant/` and `api/gateway/` rather than the flat `{use_case}/agents/`
pattern. New use cases with a similar split need two sub-agent files following
the same pattern.
