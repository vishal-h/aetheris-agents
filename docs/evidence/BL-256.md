# BL-256 — scheduler overlap: a due schedule starts a new run while its previous run is still live

**The finding.** `Aetheris.Scheduler` starts a run for every due row and never asks whether that schedule's previous run is still live: `start_scheduled_run` calls `Aetheris.start_run/1` and then advances the schedule (`lib/aetheris/scheduler.ex:81-90`), and the moduledoc calls the scheduler *"fire-and-forget: it does not wait for runs to finish"* (`:11`). No overlap policy is recorded in the design (`docs/aetheris/milestones/m13-persistent-agents.md:164`) or in `m13-t2-implementation-notes.md`. A schedule whose run outlasts its interval therefore stacks runs.

`Source: filed 2026-09-15 by claude-code at agents `633b4e5`, from BL-200's audit of the moadim brief's Cluster 2 (`docs/evidence/BL-200.md`, close block), item 1. Harness read at `83a79c5`; every line cited above was opened by the filing session.`

> **[Closed 2026-09-16: `state: done`, disposition `fixed`.]** Harness fix commit `89d0039`, T2 of `m-scheduler-hardening`, extending INV-2's chokepoint (`65bec46`) under INV-1 (`92e9afa`).
> - **A reason, not a path.** `Admission.decide/2` gains one `cond` arm beside the pause and cap arms; `refusal_reasons/0` is now `[:global_pause, :overlap_live, :cap_full]`, and that list **is** the check order. The atom is `:overlap_live`; the row's `overlap-live` is prose, ruled so by the arbiter at the T2 scout.
> - **The run↔schedule association is a `scheduled_runs.last_run_id` column**, written by the chokepoint at admission for every schedule-bearing start — so the tick and the manual trigger record through one point, closing BL-258's cite that the trigger path recorded neither. The registry could not carry it: `{:server, run_id}` holds a `nil` value, the registry is `:unique`, and an entry belongs to the process that registered it. An `Admission` state map and a name threaded into `Agent.Server` state were both rejected for losing the association across a restart — a boot-resumed run would stop being detectable and the check would return a clean `false`.
> - **Only the association is stored; liveness is rebuilt** from the run registry by the same predicate `live_count/0` uses, which is the half INV-2 requires be state-from-reality. A test asserts the split directly: the association survives a run's termination and the decision flips on liveness alone.
> - **Identity is `opts` metadata, never `RunConfig`.** `start_run/2` takes `schedule:` beside `origin:`, set by the two lib call sites. `RunConfig.schedule` holds a caller-supplied cron *expression*, which is not an identity — two schedules can share `* * * * *` — and nothing reads it.
> - **Absent schedule context is not-applicable, not a refusal.** `decide/1` delegates to `decide/2` with `nil`. The test makes the point at the only moment it can be made: at the same instant that schedule is refused, a start belonging to no schedule is admitted.
> - **`Admission.disposition/1 :: :defer | :skip`**, extensible alongside `refusal_reasons/0` rather than a scheduler branch. The tick is the **only** caller that acts on `:skip`, being the only one that owns a schedule cursor — it records `:schedule_skipped` and advances; `trigger_scheduled_run/1` returns the refusal, advances nothing, records nothing. A test asserts every member of the reason set has a disposition, so a later row cannot add a reason without one.
> - **The skip event.** `:schedule_skipped`, payload `schedule` / `reason` / `skipped_fire_at`, emitted the way `sweep.ex` emits `:run_orphaned`, under the pseudo run id `schedule_<name>` (`Scheduler.schedule_event_run_id/1`). Nothing treats it as a run: `events.run_id` carries no foreign key and every enumerator of runs reads the `runs` table, which has no such row — `Sweep`, the CLI and API run surfaces, and Rig, which lists runs from `runs` (`docs/rig/specs.md` §2). `step` is `0` — not a step in a run — and `seq` carries the order.
> - **A defect found by this round's own test.** `advance_schedule/1` had stamped `last_run_at` since m13. Harmless while it ran only after a *successful* start; this row makes it run on the **skip** path, where no run started, so it claimed a fire that never happened — and it would have corrupted BL-258's dedup window, which is keyed on that column. Narrowed to write `next_run_at` only, at the source rather than in the assertion. Two existing scheduler tests read the column and pass unedited.

The whole-suite gate caught it; the per-file runs did not. cc extended the enumeration, the in-scope repair: deriving the map would also close the `:observation` gap, which is **BL-206's** and not this row's to dispose of. BL-260 adds `:schedule_missed_fires` and must edit both surfaces.
