# BL-257 — no global concurrency cap: nothing limits how many runs the harness admits at once

**The finding.** Runs are children of `{DynamicSupervisor, name: Aetheris.RunSupervisor, strategy: :one_for_one}` (`lib/aetheris/application.ex:45`), declared without `max_children`, and nothing else in `lib/` limits admission (`grep -rn 'max_children' lib --include=*.ex` → 0; same flags on `strategy` → 39). The moadim brief's rule is a cap derived from live runs, so that it survives a restart, which is BL-003's state-from-reality approach applied to admission.

> **[Closed 2026-09-16: `state: done`, disposition `fixed`.]** Harness fix commit `65bec46`, which **establishes INV-2** — the single admission chokepoint, its cap, and its refusal set. The done-when was amended at this close to state, verbatim, that the cap is a production admission cap and not an absolute process/resource ceiling.
> - **One chokepoint.** `Aetheris.start_run/1` routes every start through `Aetheris.Admission` (`../aetheris/lib/aetheris/admission.ex`). The tick path (`scheduler.ex:86`) and the trigger path (`aetheris.ex:361`) reach it through `start_run/1` rather than through paths of their own, and so do the other seven lib callers — CLI `run`/`fork`/`replay`, `fork_run`, the playground router, the eval runner and `llm_judge`. The scout census that found those nine callers is why admission sits inside `start_run/1` rather than beside the scheduler.
> - **Admitted or refused with a named reason.** `Admission.refusal_reasons/0` is the extensible set, `[:cap_full]` at this row. Reasons are bare atoms, so `api/router.ex:111`'s `Atom.to_string(reason)` keeps working — a tuple refusal there would have become a 500.
> - **The cap.** `:max_concurrent_runs`, default **4**, in `config/config.exs` with the reasoning at the setting. A persisted `harness_flags` row overrides it; an unparseable override loses to the config key.
> - **Rebuilt, never tallied.** `Admission`'s state is `%{}`. The count is derived on every admission from the run registry, over `:idle`/`:running`/`:paused` servers. Counting `:idle` is what closes the race — the child registers during `start_child`, before its loop starts — and it is the state a boot-resumed run is restored into.
> - **Serialised.** The check and the supervisor start are one `handle_call`, because a check-then-start pair admits N+1 under two concurrent starts.
> - **Eval exemption is unforgeable.** It travels as `start_run(config, origin: :eval)` from the two lib call sites, never as a `RunConfig` field: `from_map/2` reads a fixed key list, so an `"origin"` key in a playground body or a stored schedule template is dropped. A test asserts the forged key is dropped *and* that the run is still refused.
> - **Deviation — children.** The origin table gates child agents "at `start_run/1`"; they cannot be, because `spawn_agent` does not go through it. Children are gated by the same admission function (`Admission.admit_and_supervise_child/1`) but start under `Agent.DynamicSupervisor`, because routing them through `start_run/1` would move them under `RunSupervisor` and destroy the m12 isolation property. The cap and the decision are identical; the supervisor is not. Recorded in `../aetheris/docs/aetheris/milestones/m-scheduler-hardening-t1-implementation-notes.md`.
> - **Tests.** `../aetheris/test/aetheris/admission_test.exs`, 11 tests: the (N+1)th refused at the chokepoint and through `Aetheris.start_run/1`; the reason set; the config default and store override; eval admitted at the cap and counted past it; the forged-origin refusal; child backpressure naming `cap_full`; and two rebuild tests.
> - **Red-by-mutation.** `>=` → `>` on the cap comparison: 8 of 11 red. The registry derivation replaced by `0`: 8 of 11 red. Each restore was made from a working-copy backup — never `git checkout --`, which would have restored to HEAD — and verified by sha against that backup (`654d97815f845dc8` both times), with the restored tree re-run green.
> - **The restart arm, and what each half proves.** Killing `Admission` with live runs present is the half that discriminates a derived count from a stored tally: a tally would read 0 after the restart and admit past the cap. The full harness restart (file-backed store, `Application.stop/ensure_all_started`) proves the persisted cap survives and the count comes back from an empty registry rather than from a carried number. Neither alone would establish it.

Any finite test cap is order-dependent. The measurement is recorded rather than the number quietly raised.
