# BL-258 — same-minute double fire: a manual trigger and a due tick both start runs for one schedule

**The finding.** Two paths start runs from one schedule template. The tick path starts the run and then advances `next_run_at` (`lib/aetheris/scheduler.ex:71-74`, `:86-90`). The trigger path, `Aetheris.trigger_scheduled_run/1` (`lib/aetheris.ex:340-349`, reachable from `cli/commands/schedule.ex:88` and `api/router.ex:103`), neither reads `last_run_at` nor advances the schedule. A trigger in the same minute as a due tick starts two runs.

> - **One point, not two.** `Admission.decide/2` gains one predicate, `duplicate?/1`. Both paths reach it through `start_run/2`'s `:schedule` metadata, so there is nothing per-path to keep in step. Tested in **both directions** — trigger-then-tick and tick-then-trigger — which is what separates one shared point from two that merely resemble each other: a guard in only one path passes one test and fails the other.
> - **Checked before `:overlap_live`, deliberately.** A same-minute second attempt usually *also* has its first run live, so under the reverse order this guard would answer every case it was written for with the other reason — observationally invisible, and an ineffective guard would look exactly like a working one. `refusal_reasons/0` is now `[:global_pause, :duplicate, :overlap_live, :cap_full]`, which is the check order.
> - **The window is the UTC minute**, both sides parsed and truncated rather than compared as string prefixes — `last_run_at` may have been written by any path and two ISO 8601 strings for one minute need not share a prefix. Cron's finest granularity is one minute, so a per-minute window can never suppress a legitimate second fire of the same schedule. A boundary test asserts a *different timestamp in the same minute* still refuses while one minute earlier does not, so "same minute" is not quietly "same instant".
> - **It reads `last_run_at`**, stamped by the chokepoint at admission on every schedule-bearing path (BL-256), so a duplicate is caught whether the first start came from the tick or the trigger and **whether or not that run is still running** — which no live-run scan could do, and which is why the dedup fact had to be persistent.
> - **`disposition(:duplicate)` is `:skip`.** The tick records `:schedule_skipped` with `reason: "duplicate"` and advances. A refused trigger advances nothing **and records nothing** — it owns no schedule cursor, and an operator-initiated action has a synchronous channel that is its own audit trail. A test asserts both halves, including that the schedule's event stream is empty after a refused trigger.
> - **Both paths honor INV-1**, each with a **positive control** so the nothing-happened is the pause rather than an absence: under pause the tick writes no `last_run_id`, `last_run_at` or `next_run_at` and the same tick fires once unpaused; the trigger returns `{:error, :global_pause}` and succeeds once unpaused. `INV-1 still precedes it` asserts the order with the duplicate condition true at the same moment.
