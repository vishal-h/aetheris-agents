# BL-260 — missed fires catch up silently: a schedule due while the harness was down runs on startup, with no alert

**The finding.** On startup the scheduler ticks at once (`lib/aetheris/scheduler.ex:50-52`). The due query starts every row with `next_run_at <= now` (`lib/aetheris/store.ex:1982`), and `advance_schedule` recomputes from now (`scheduler.ex:103-111`), so any number of fires missed while the harness was down collapse into one catch-up run, launched with no alert. The moduledoc describes the behaviour (`:5-6`, *"On startup it immediately checks for any runs that were due while the application was down"*), and no record weighs it against alert-only. The moadim brief's reason this must be a stated rule: a scheduled run here can carry irreversible effects (payslip release, cleanup execution). Filed by omission; the arbiter may rule it deliberate on the moduledoc's ground.

A fire that passed while the harness was down starts **no run**; the schedule is alerted and advanced past it.
> - **The startup path is now distinguishable**, which it was not: `handle_continue(:start, _)` sent the same `:tick` message the 60s timer sends, so nothing separated a catch-up from a periodic check. The sweep runs **inline in `handle_continue`, before** the first tick. That order is load-bearing: it advances the affected rows so the following tick finds them not due, where the reverse would let the tick fire the very occurrence the sweep is about to declare missed.
> - **Regardless of pause, without loosening the due query.** `Store.list_due_scheduled_runs_ignoring_pause/1` calls the existing `do_list_due_scheduled_runs_unpaused/2` directly; `do_list_due_scheduled_runs/2` is untouched and every other caller still gets `{:ok, []}` while paused. Its test carries the control that makes the claim readable: inside the pause it first asserts `list_due_scheduled_runs/1` returns `{:ok, []}`, so the alert that follows is demonstrably firing through a query the pause has already emptied for everyone else. `enabled` is **not** dropped — a disabled schedule is not alerted, asserted separately.
> - **The interval arithmetic was fixed before any test was written**, so implementation and tests could not each pick a convention. `t0` is the first cron occurrence at or after `next_run_at`; **N counts every occurrence `t` with `t0 ≤ t ≤ now`**, including the currently-due one, and an occurrence falling **exactly on `now` counts as missed**; the row advances to the first occurrence **strictly after** `now`. It is written in `Scheduler` beside the code and in the test module's `@moduledoc`, and three tests pin the boundary separately.
> - **`Crontab.Scheduler.get_next_run_date/2` is inclusive — probed, not assumed.** For `0 9 * * *` at `~N[2026-05-20 09:00:00]` it returns that same instant. So the walk steps `+1s` past each occurrence and the advance is strictly-after by construction. Inclusive-of-now is also the deterministic choice: the sweep runs milliseconds after boot, so an exclusive boundary would classify the same fire differently from one boot to the next.
> - **Two edges, stated and tested.** `N = 0` — a due `next_run_at` on which no occurrence falls at or before now — alerts nothing and advances nothing; the ordinary tick governs. An unreadable cron or timestamp is reported and the row left exactly where it is, rather than alerted with a count derived from nothing.
> - **The walk is capped at 10,000**, and a capped count ships **as capped** (`missed_count: 10_000, truncated: true`) rather than as a figure the sweep did not derive. A minutely schedule a year stale is over half a million occurrences.
