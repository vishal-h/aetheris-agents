# BL-261 — retention family: no solo-run max-runtime stop, and no reaping or eviction of run artifacts

**The finding.** *Watchdog:* `RunConfig.max_duration` exists (`lib/aetheris/run_config.ex:118`) and `mix aetheris run --max-duration` sets it (`cli/commands/run.ex:17`, `:64`), but its enforcement was *"deferred to m09+"* (`docs/aetheris/milestones/m08-cli-validation-sprint.md:29`) and no `lib/` consumer enforces it. Only orbs have a runtime stop (`orb/coordinator.ex:172-177`, `max_runtime_ms`). *Retention:* `lib/` has no reaping, TTL or eviction site (`grep -rn -iE 'rm_rf|File\.rm|cleanup|clean_up|prune|purge|delete_run|retention|older than|max_age' lib --include=*.ex` → 0; same flags on `orphan|sweep` → 77). Keeping a verify overlay on disk after its run is deliberate (`execution/verifier.ex:171-174`), but nothing records when, if ever, overlays and run directories are reaped. Filed against the retention family, per BL-200's done-when.

> - **`:failed`, not a new status.** The terminal status is `:failed` — the orb's own `:orb_timeout` already does this (`orb/coordinator.ex:176`) — and the distinguishing detail rides a new `run_timed_out` event, which is the immutable record. A `:timed_out` status member was costed and rejected: nine sites, of which `cli/commands/run_helpers.ex`, `eval/runner.ex` and `eval/scorer/llm_judge.ex` each treat an unrecognised status as *still in progress* and would poll to their own deadlines rather than error — three silent hangs for one atom — plus `docs/rig/specs.md:29` and `:506`, whose documented status union already omits `cancelled`, so widening it meant first repairing a pre-existing gap in the other repo.
> - **"Decrements INV-2's live count" is satisfied by driving the run terminal.** There is no counter: `Admission.live_count/0` rebuilds from the run registry by status (state-from-reality). The test is the one the row names — at the cap, a start refused `:cap_full` succeeds after the watchdog stops the run holding the slot.
> - **Event before status, and the sweep clause is what makes that safe.** `time_out_state/1` appends `run_timed_out` **before** the `runs` upsert, so a harness dying between the two leaves a terminal trajectory over a `running` row. `Sweep.terminal_status(:run_timed_out) -> "failed"` reconciles exactly that. Without the clause the run is classified **orphaned** instead — which also marks it `failed`, so the row alone cannot tell the two apart; the tells its test asserts are the ones that can (no `run_orphaned` event appended, `finished_at` from the timeout's own timestamp).
> - **A parser had to be written.** `RunConfig.max_duration` has been a raw string enforced by nothing since m08; there was no duration parser anywhere in `lib/`, the orb's stop taking an integer `max_runtime_ms`. `Aetheris.Duration.parse/1` takes `<positive integer><s|m|h|d>` and refuses everything else — no compound forms, no bare integers. Seconds are not an m08-documented form; they are here because a test needs a budget it can wait out, and accepting them accepts every documented form unchanged.
> - **Unparseable never means "no limit" silently.** An unparseable value arms no watchdog, so `mix aetheris run` validates `--max-duration` before the agent file is even loaded. Without it a typo starts a run with no time limit and reports a successful start.
> - **Two deviations from the plan, both forced by scouting the resume path, both reported rather than absorbed.** (1) `Agent.Server.encode_config/1` **stripped** `max_duration` from `config_json`, and `RunConfig.from_map/2` never read it — so a resumed run's reconstructed config carried `max_duration: nil` and the approved resume-arming would have been dead code. Both were fixed, per critical rule 15's (c). The scheduled-run *template* still strips it (`Aetheris.encode_run_config_template/1`); that is BL-262's question, deliberately untouched. (2) `handle_cast({:write_checkpoint, ...})` wrote **unconditionally**, whatever the status, so the still-running loop Task could re-create the checkpoint the stop had just deleted and hand the run back to boot resume. Guarded on terminal status. This also repairs the same hole on the **cancel** path, where `cancel_state/1` has deleted the checkpoint since m10 and that deletion was only ever as durable as the loop's next step.
> - **The restart test is deterministic, and its first form was silently vacuous.** Backdating `started_at` with `Store.upsert_run/2` after the run starts is a **no-op**: the `ON CONFLICT` arm deliberately does not update that column. The row is therefore seeded with a backdated `started_at` **before** the run starts, where `INSERT` honours it. The resumed run reads 20 minutes elapsed against a 10-minute budget and stops at once — the run logs `stopped by the max_duration watchdog after <elapsed>ms (max_duration "10m")` with an elapsed of about twenty minutes — where a fresh budget would still be running ten minutes later. `[The figure was `1200041ms` as first written 2026-09-16. > **[Closed 2026-09-16: `state: done`, disposition `fixed`. 261b — the retention half.]** Harness commit `7257ca3`, T3 of `m-scheduler-hardening`. Both arms built; neither arm ruled out.
> - **One definition of live, and it is admission's.** `Aetheris.Admission.live?/1` and `live_run_ids/0` were made public and `Aetheris.Retention` calls them; retention has no predicate of its own. A second notion of liveness that could disagree with admission would be free to delete the artifacts of a run the harness still considers running.
> - **Live and finished are different questions, and both are asked.** `live?/1` answers *is this run occupying the node now*; it cannot answer *has this run finished*, because a finished run from a previous harness process is equally not-live. The `runs` table answers the second. Five categories, stated in the moduledoc and the runbook: `live`, `claimed_running`, `claimed_finished`, `unclaimed`, `unrecognised`.
> - **The three-category finding is the design's motivation, and collapsing it is the absent-is-unknown trap.** Measured at harness `a804ae5`: `priv/runs` held 59,705 directories over 2.8 GB, against 1,149 rows in `runs` — **1,057 directories claimed by a row, 58,648 unclaimed, 92 rows with no directory** (`ls priv/runs | sort` and `sqlite3 priv/aetheris.db "select run_id from runs" | sort`, compared with `comm`). Reading "finished-only" as terminal-row-only would have made the ceiling arm decorative, since the disk is almost entirely the category such a rule cannot touch. **Unclaimed is not finished** — the harness has no record of the directory, which is why eviction additionally requires it to clear a grace window.
> - **The grace window is a new config key and it exists for a race.** A run's directory exists before its row is written, so without `:run_artifact_evict_grace` (default `"1h"`) a just-started run's artifacts are evictable out from under it — the BL-263 registration-race class. The TTL arm needs no grace key: at 90 days it clears any startup window by construction.
> - **Two things the real tree taught, neither of which was in the plan.** (1) Overlay `work/work` directories are created mode `d---------`, so `File.rm_rf/1` returns `:eacces` on a run through no fault of its own — 15 appeared in a single `du`. A failure is counted against its directory and the sweep continues; `execute/2` returns `{:partial, summary}` naming what it could not remove. A sweep that aborted on the first undeletable overlay would never reach the rest of the tree. (2) The root contains **a nested copy of itself**, `priv/runs/priv/runs/…`, because an `overlay_base_dir` pointed inside the root re-joins `priv/runs`. A top-level entry named `priv` is not a `run_id`; under the eviction rule alone it is unclaimed and old, and removing it would delete other runs' overlays. Such an entry is categorised `unrecognised` — **reported and never touched** — rather than swept up or silently skipped.
> - **On demand only, and dry-run by default.** Neither arm runs on a timer or at boot. `mix aetheris reap` is the only caller; it surveys and prints and removes nothing unless `--execute` is passed, the BL-194 precedent for a destructive command. It also takes `--root`, an injected base path, which is a **safety boundary rather than a convenience** — see the test-design defect below for why it exists. **The deferred alternative is named rather than left implicit: a boot-plus-interval reaper on the same config keys is a backlog row of its own, not this one** — automatic irreversible deletion of an operator's artifacts earns its own ruling.
> - **Verify overlays are RULED OUT of retention scope, on the record.** They live under `System.tmp_dir!()` rather than `priv/runs`, the OS reaps that tree, and `Execution.Verifier` keeps them deliberately so an operator can inspect what a verify wrote (`verifier.ex:160-174`) — reaping them would undo another row's decision. Checkpoints are likewise out: they are `run_checkpoints` rows, not disk artifacts, and deleting one changes resume semantics.
> - **Conservative defaults, stated as the ticket requires**: `:run_artifact_ttl` `"90d"`, `:run_artifact_disk_ceiling` 5 GiB, `:run_artifact_evict_grace` `"1h"`. The ceiling sits above what the tree holds, so landing this removed nothing; an operator opts in by lowering either. A test reads the defaults out of `config/config.exs` rather than application env, as `admission_test.exs` does for the cap.
> - **THIS ROUND'S OWN TEST-DESIGN DEFECT, named rather than filed.** The first form of the dry-run test ran against the **real** `priv/runs`, on the reasoning that the default invocation is the one an operator types by accident and must be safe there. Mutating the dry-run clause — which a mutation test does **on purpose** — therefore executed a real 90-day reap: roughly **fifteen thousand run directories removed, irreversibly** (63,007 → 47,746 entries, 2.9 GB → 2.0 GB; rows with no directory 92 → 761, so 669 runs kept a row and lost their trajectory). `priv/runs/*/` is gitignored dev scratch, so there was nothing to restore from. **The defect is the test, not the command**: a destructive command's tests must be sandboxed *by construction*, because mutation testing deliberately removes the guard that would otherwise protect real data. The fix is `--root`, an injected base path, and the rule that **no test in `retention_test.exs` may resolve to the real tree, ever** — stated in that file's moduledoc so a later row cannot reintroduce one. The re-run carries its own control: the real tree is 47,746 entries before the mutation sweep and 47,746 after. The **669 now-dangling rows are left alone** — they are the claimed-finished-with-no-directory category the design already accounts for, 92 of which pre-existed, and reconciling them by hand would mutate the dev store ahead of the tooling meant to do it. Same class as BL-257's ambient-count defect and 261a's fixture child-diff: a test whose environment, not whose logic, was wrong.
> - **And a second test defect, in 261a's own frees-admission test, fixed here.** It asserted `live_count() == occupied - 1` — exact arithmetic on a global total — and failed once on the damaged-tree gate with `left: 8, right: 10`, three ambient runs having departed between the two readings. That is the hazard `admission_test.exs` records against seed 31337, and the assertion was fragile from the moment it was written; it passed until the suite happened to be busy enough. It now asserts about **this** run — `refute Admission.live?(run_id)` plus `live_count() < occupied` — which is what the test was ever about and is immune to ambient churn. The mutation that proves it (the watchdog not driving the run terminal) still reds it, re-verified after the rewrite.
> - **Red-by-mutation, seven guards, seven reds**, each reding its own: the liveness gate dropped → both arms' live tests; the grace check dropped → the young-unclaimed test; the sort reversed → the oldest-first test; the dry run made to execute → the dry-run test; TTL's non-terminal exclusion dropped → its own test; `run_shaped?` forced true → the unrecognised test; a removal failure made to raise → the partial test. **The sort mutation's first form was malformed** — `Enum.sort_by(entries, :desc, fn)` is `sort_by/3`'s mapper-plus-sorter form, so it crashed and its 12 reds proved a crash rather than that ordering is load-bearing; redone as a valid newest-first sort, it reds exactly the ordering test. Restores from working-copy backups, sha-verified.
