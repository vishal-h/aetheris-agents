# BL-263 — a boot-resumed run is not yet registered when the scheduler's first tick runs, so `:overlap_live` cannot see it

**The finding.** BL-256's overlap check rebuilds liveness from the run registry, so it sees a boot-resumed run *once that run's `Agent.Server` has registered*. At boot it has not. `Aetheris.Application.start/2` starts `Aetheris.Scheduler` as the last child of `Supervisor.start_link` (`lib/aetheris/application.ex:41-50`), and the scheduler's `handle_continue(:start, _)` sends itself `:tick` immediately (`lib/aetheris/scheduler.ex:50-53`). `resume_checkpointed_runs/0` runs **after** `Supervisor.start_link` returns (`application.ex:55-58`). So a due schedule fired by that first tick is admitted against a registry that does not yet contain its own previous run, and `:overlap_live` returns false where it should return true — a silent second start, the exact condition BL-256 exists to prevent.

**The window, so it need not be re-derived.** It opens when the scheduler's first tick runs and closes when `resume_checkpointed_runs/0` finishes. **At the commit that files this row** (BL-256's) that is the whole of it, and it covers every schedule already due at boot. BL-260's startup missed-fire sweep — landing later in T2 — advances every row *already due at boot* past its missed fires before the first tick, which removes that part; what it cannot remove is a row that **becomes due between the sweep and the first tick**. Re-derive the residual window against the tree at BL-260's close rather than trusting this sentence.

**What is deliberately not done.** Ordering `resume_checkpointed_runs/0` ahead of the scheduler is a supervision-tree change, out of scope for T2 and ruled so by the arbiter at the T2 scout. This row carries it rather than the packet's prose, because prose has no executor.
