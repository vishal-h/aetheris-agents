# BL-264 — the test suite's live `Aetheris.Scheduler` fires other modules' residue schedule rows, starting untracked runs mid-suite

**The finding.** `Aetheris.Store.ScheduledRunTest` inserts `sched-test-*` rows into the store and does not remove them (`test/aetheris/store/scheduled_run_test.exs:7`). The harness's `Aetheris.Scheduler` runs for the whole suite, ticking on its 60s timer (`lib/aetheris/scheduler.ex:38`, `:84`) and again at every boot (`handle_continue(:start, _)`, `:50-53`) — and `Aetheris.Test.HarnessRestart.with_file_store/1` reboots the harness twice per use, the second time back onto the `:memory:` store holding that residue. Each such boot starts a run for every due residue row. Observed as a burst of five starts inside 61ms at harness `a804ae5` + BL-261a: `19:10:01.330`, `.345`, `.358`, `.378`, `.391`, all `[Aetheris.Scheduler] started run … for schedule 'sched-test-…'`.

**What it costs.** These are real runs: they take admission slots, and they write `priv/runs/{run_id}/` trajectories that nothing removes. They have already bitten cap arithmetic once — `test/aetheris/admission_test.exs:19-22` records seed 31337, where "another module's leftover run can finish mid-test, drop the live count below the cap, and admit the run this test expects to be refused", and the occupy-then-pin idiom there exists to work around it.

**What BL-261a already fixed, and what it did not.** BL-261a made `Aetheris.Test.Admission.admit_live_run/1` resolve its run from the `run_id` rather than by diffing `RunSupervisor`'s children, so a concurrent start no longer returns `{:error, {:ambiguous_child, [pid, pid]}}`. That removes the *collision* this residue was causing. It does not remove the residue, the untracked runs, or the trajectory directories they leave behind.

Every line cited above was opened by the filing session.`
