# BL-266 — no streaming transport for run/trajectory updates: a UI must poll

**The finding.** The harness HTTP API (`lib/aetheris/api/router.ex`, harness `191970a`) answers every endpoint with a single complete JSON body (`Plug.Conn.send_resp` + `Jason.encode!`); there is no chunked response, no `text/event-stream` (SSE), and no WebSocket anywhere in the harness repo. A UI following a run therefore polls `GET /api/runs/:id` and `GET /api/runs/:id/trajectory`, and the latter returns only a summary (`step_count`, `event_count`, `event_types`), not the event payloads. Rig reads full event bodies out of band — a Tauri command against the SQLite store — not over HTTP.

**Why filed.** A UI is being connected to the harness (2026-09-17). Trigger (`POST /api/runs`, `POST /api/playground/runs`) and poll work today; live push does not exist. Both an HTTP stream and a WebSocket are wanted.

**Design constraint (not a ruling — for whoever scopes it).** The push must be driven by the event-append site so the stream is a fan-out of the one write path, not a server-side poll that reintroduces the polling this row removes (the repo's state-from-reality / single-chokepoint posture). The connect-time contract (from-now vs replay-then-live), the SSE-vs-chunked choice, and whether SSE and WebSocket split into two rows are the scoping round's to decide and record.
