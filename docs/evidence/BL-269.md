# BL-269 — multiple VMs write one store: every CLI command boots its own Store, Scheduler and sweep on the same file

**The finding.** Harness at `191970a`:
1. **Every `mix aetheris <cmd>` boots a full application.** `RunHelpers.ensure_started/0` calls `Application.ensure_all_started(:aetheris)` (`lib/aetheris/cli/commands/run_helpers.ex:345-351`), which starts `Aetheris.Store` and `Aetheris.Scheduler` and runs the startup sweep (`lib/aetheris/application.ex:41-62`), all on the configured `db_path`.
2. **Sweep's liveness check is node-local.** `live?/1` reads only this VM's `Aetheris.Registry` (`lib/aetheris/sweep.ex:217`), so a stale-looking run live in another VM can be failed. Inferred, not observed.
3. **Competing Schedulers compute the same `seq`.** `next_seq/1` is `max_event_seq + 1` in one Store call and the insert is another; a `UNIQUE` conflict is logged and the event dropped (`lib/aetheris/scheduler.ex:184-200`).
4. **A Sweep insert crashes another VM's live run.** That run's `Log` holds `seq` in memory; its next append conflicts and returns the error (`lib/aetheris/trajectory/log.ex:105-111`), and callers match `:ok = Log.append(...)` (e.g. `lib/aetheris/agent/server.ex:578`).

Ruling 2026-09-25 (the arbiter's): BL-269 closes by the guard route. Preferred form: a `mix aetheris <cmd>` VM does not start `Aetheris.Scheduler` or the startup sweep; whatever does start them holds a single-writer guard on `db_path` and a second VM is refused with a named error. Cross-VM coordination is out of scope. Sized S–M on this route.
