## Where `mint` enters, and whether a fix exists

**Transitive, two levels down.** It is not declared in `aetheris/mix.exs` — the declared HTTP
deps are `{:req, "~> 0.5"}` (`:28`) and `{:bandit, "~> 1.12"}` (`:30`). From `mix deps.tree`:

```
├── req ~> 0.5 (Hex package)
│   ├── finch ~> 0.21 (Hex package)
│   │   ├── mime ~> 1.0 or ~> 2.0 (Hex package)
│   │   ├── mint ~> 1.8 (Hex package)
```

**A newer version exists and nothing holds it back.** From `mix hex.outdated mint`:

```
There is newer version of the dependency available 1.10.1 > 1.10.0!

Source  Requirement  Up-to-date
finch   ~> 1.8       Yes
```

`finch`'s `~> 1.8` admits 1.10.1, so this is a lockfile bump rather than a constraint problem.
**Whether 1.10.1 clears EEF-CVE-2026-82672 is NOT established here** — neither command says so,
and 1.10.1 being the next patch is suggestive, not evidence. The direct test is the bump plus a
re-run of `mix hex.audit`, and it belongs to the fixing round. No upgrade was performed.

**Exposure, as far as those two facts carry it.** `mint` is reachable only through `Req` →
`Finch`, on the outbound provider path: the `Req.` callers in `lib/` are the four LLM adapters
(`anthropic.ex`, `openrouter.ex`, `gemini.ex`, `ollama.ex`), and `lib/` contains no direct
`Mint.` call. The playground API server is Bandit over ThousandIsland and does not reach it, so
the advisory is not on the run-event-stream path. Whether the advisory's own precondition — a
strict intermediary in front of pooled connections — is reachable on the outbound path is
**not settled by these commands**: it depends on whether a proxy sits between this harness and
the provider endpoints, which is deployment configuration and was not read.
